# LAN starter session

The fork can create a four-track generated MIDI starter or explicitly share a musical copy of
an open MIDI project. The [MIDI-copy contract](lan-midi-copy.md) defines supported music and
its additional validation. Both cases create a dedicated restricted tab and retain the original
projects. The host owns canonical controls; each app renders its own copy with independent
play/stop/seek. Only track name, volume and pan are live shared edits. Notes and clips are sent
as initial music, then remain read-only while connected. Audio and plugins are not transferred.

## Invitation and connection

Starting is explicit. The host binds one user-selected private or loopback IPv4 address and
an ephemeral port. No listener exists before this action; no discovery, public relay or account
is used. The UI can suggest the route's private local address without sending a UDP datagram.
Public IPv4 addresses and DNS targets are refused for this milestone.

The invitation contains protocol 2, address, the host's self-signed TLS certificate and a
256-bit OS-random admission secret. It is copyable but never logged or persisted. Its Debug
representation is redacted. The invitation expires after five minutes and is redeemed once.
Stopping revokes it. One guest is admitted. An old invitation does not resume a disconnected
peer; create a fresh host session to invite again. Both apps need protocol 2; protocol-1
invitations and connections are incompatible and refused before any document is sent.

TLS 1.3 uses rustls and a certificate generated by rcgen for suhina.local. The guest trusts
only the certificate in the invitation, verifies that name and normal handshake signatures,
then proves possession of the secret inside TLS. The hello names MIDI-copy format 1.
No insecure verifier is used. The stored secret hash is compared in constant time. Neither a
valid TCP connection nor a numeric local peer handle authorizes a document download or edit.

## Bounded exchange

Typed JSON messages have a four-byte big-endian byte length, capped at 65536 bytes before body
allocation. This covers 64 bounded track names including JSON escaping. Control characters in
names are refused. Empty/oversized/truncated frames and unknown/duplicate envelope fields fail.

After admission, the guest pulls the canonical MIDI document in 4096-byte chunks at exact offsets,
with a 2 MiB total cap, SHA-256 verification and an absolute 30-second transfer deadline. Its JSON
shape, native version, musical subset and exact canonical encoding are checked before opening a
tab. No arbitrary file paths, extension blobs, plugin states or assets reach project preparation.
No transfer files are written. The ordinary handshake/request deadline remains three seconds.

The guest then sends a poll or one edit with its sequence and base revision. The host maps it to
its authenticated PeerId and uses the existing collaboration Host and Edit allowlist. Replies
contain the complete bounded track-control snapshot and acceptance/rejection. Unknown track IDs
fail in canonical execution. Stale edits are visibly refused, never silently rebased/retried.
Accepted sequence numbers advance only after acceptance. Poll rates, pending handlers and queues
remain bounded as before. An old or incompatible invitation cannot silently join a demo instead.

Snapshots may skip revisions because they contain every track control. The guest validates all
fields and the exact track ID/order against its verified music before applying any, rejects
backwards revisions and rejects changed controls under the same revision. The host can adjust
controls during the initial download; its final snapshot is applied over the immutable initial
music. Local transport never enters the wire or increments the shared revision.

## Desktop boundary

The app opens a new shared MIDI tab; it does not overwrite, replace or save the source project.
The mutation gate admits only authoritative controls through the host-owned API. Normal UI and
attached-agent commands cannot edit the shared model/history. Private play/stop/seek and local
save/export remain available; network admission is not offered to agents. Leaving/disconnect
retains and unlocks the last local copy for normal solo editing. Other tabs stay local.

Networking, document encoding/decoding and canonical-host execution run off the audio thread.
The UI stages a checked local project; workers prepare and validate its restricted document.
A missing/invalid/incomplete document opens no guest tab and never falls back to generated music.

## Validation and limits

Tests cover real TLS starter and custom-project exchanges, non-contiguous track IDs, multiple
chunks, equal musical data and real audio renders, invalid certificate/secret/version, expired or
reused admission, stale/replayed operations, malformed frames, wrong size/hash/offset, partial
transfers and cancellation. UI tests cover current-project sharing, refusal of audio without a
listener, original-tab preservation and unlocking on disconnect.

Physical two-computer/firewall and cross-platform session acceptance remain later checks. The
MIDI copy is not full project coediting or portable media exchange: shared note/clip editing,
audio assets, recording publication, additional instruments, linked transport, Internet routing,
reconnect/resume, presence cursors and host migration remain future work.
